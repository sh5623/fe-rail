# 회귀 테스트 확인 (test-verify)

> 새로 쓴 회귀 테스트가 **수정 전 코드에서 실제로 실패하는가**를 잰다. 통과하는 테스트가 그 결함을 정말 잡는지는
> 테스트를 다시 돌려서는 알 수 없다 — 고친 줄을 되돌렸을 때 빨개져야 그 테스트가 그 결함을 지킨다.
> 이 문서는 실행기가 미검출 · 원인 미확인 · 측정 불가를 낼 때 출력하는 해석 문서이자 기능 설명서다.

## 1. 언제 도나

| 경로 | 동작 |
|---|---|
| 종료 훅(`test-verify-stop.sh`) | 이번 턴에 단위 테스트를 바꾸고 관련 제품 소스도 바뀌었는데 현재 상태와 맞는 기록이 없으면 종료를 **한 번** 막고 실행기 명령을 지시한다. 두 번째 종료는 막지 않는다 |
| `fe-start` Phase 4.5 | 변경된 단위 테스트가 있으면 `fe-rail verify-test status` 로 기록을 확인하고, 없으면 실행기를 돌려 결과를 검증 결과 객체(`kind: test-verify`)와 PR `## 테스트` 에 싣는다 |
| `fe-test-author` `regression` 모드 | 결함을 고치며 테스트를 쓰면 실행기로 확인한다 |
| 직접 | `fe-rail verify-test …` (Claude Code 의 Bash 도구 안에서는 PATH 에 있다. 일반 셸 · CI 는 `node <플러그인 경로>/bin/fe-rail.mjs …`) |

훅이 막지 않는 경우: git 저장소가 아님 · 턴 시작 기록 없음 · 러너를 알 수 없음 · 테스트와 소스의 적용 관계를 알 수 없음 ·
문서 · 지원 파일 · 설정만 바뀜 · 다른 패키지의 소스만 바뀜 · 검증되지 않은 조합(§8 — 알림만) · 바뀐 테스트가 상한을 넘음(알림만).
훅은 «실행했는가» 까지만 강제하고 «검출됐는가» 는 강제하지 않는다 — 결과는 보고와 PR 에 그대로 나온다.

## 2. 명령

```
fe-rail verify-test base   [--base <rev>] [--only <소스>]… [--test <케이스 전체 이름>]… [--expect <문자열>]
                           [--cmd <명령 틀> [--format vitest|jest|exit-code]] [--json] [--keep] -- <테스트 파일>…
fe-rail verify-test mutate --file <소스> --find <원문> --replace <바꿀 내용> [--test …] [--expect …] -- <테스트 파일>…
fe-rail verify-test status [--base <rev>] [--expect <문자열>] [--json] -- <테스트 파일>…
```

- **base — 수정 전 대조**: 대조 소스 = 제품 소스를 기준 리비전 내용으로 바꾼 것. 기준 기본값은 이 세션의 턴 시작 HEAD(기록이 없으면 HEAD).
  수정을 앞 턴에 이미 **커밋**했다면 턴 시작 HEAD 에 수정이 들어 있어 대조할 차이가 없다 — `--base <수정 커밋의 부모>` 를 준다.
- **mutate — 지정 변이**: 대조 소스 = 현재 소스의 지정한 한 곳을 바꾼 것. 새 기능이라 수정 전 코드에 대상이 없어(파일 로딩 실패)
  수정 전 대조가 측정 불가로 끝날 때 쓴다. `--find` 원문은 그 파일에 정확히 한 번 나와야 한다(0번 · 2번 이상이면 아무것도 바꾸지 않고 거절).
- **--test**: 대상 케이스. 전체 이름은 `describe > it` 처럼 « > » 로 잇는다(이름만 줘도 그 파일에서 유일하면 된다). 생략하면 기준 리비전의
  테스트 파일에 제목 문자열이 없는 케이스를 «새 케이스» 로 추정하고 출력에 `추정` 이라 적는다. 기존 케이스의 본문만 고쳤다면 지정해야 한다.
- **--only**: 대조 내용으로 바꿀 제품 소스를 일부로 좁힌다(부분 대조). 기록과 PR 에 «부분» 으로 표시되고, 전체 확인 요청을 충족하지 않는다.
- **--expect**: 대조 실행의 실패 메시지에 이 문자열이 있어야 검출로 센다(§3).
- **status**: 현재 상태에서 요청을 충족하는 기록이 있는가 — 종료 훅과 fe-start 가 쓰는 같은 판정. 미충족이면 종료 코드 3.
- 종료 코드: 0 = 실행하고 기록함(판정 결과와 무관) · 1 = 내부 오류 · 2 = 사용법 오류 · 3 = status 미충족.

## 3. 판정 — 케이스마다 넷 중 하나

| 판정 | 뜻 |
|---|---|
| **검출** | 대상 케이스가 현재 소스에서 통과했고, 대조 소스에서 그 케이스의 **본문 단언**이 뒤집혔다(`--expect` 를 줬다면 실패 메시지가 그 문자열을 담는다) |
| **미검출** | 측정은 유효한데 대조 소스에서도 통과했다 — «그 테스트가 쓸모없다» 가 아니라 «이 대조를 검출하지 못했다» |
| **원인 미확인** | 결과 차이는 있는데 본문 단언 때문이라고 확인하지 못했다(단언 오류가 아님 · 준비 · 정리 단계에서 실패 · 실패 위치를 가를 수 없음 · `--expect` 불일치 · 종료 코드만 있는 명령) |
| **측정 불가** | 결과가 판별력을 말해 주지 못한다(격리본을 만들 수 없음 · 현재 소스에서 실패 · 파일 로딩 실패 · 케이스 미수집 · 이름 중복 · 파일 · 러너 수준 오류 · 시간 초과 · 기준 스냅샷 없음 등). 사유가 함께 나온다 |

**검출의 근거와 한계**
- 단언 오류는 **필요조건**일 뿐이다. 준비 단계(`beforeEach`) 안의 `expect` 도 단언 오류를 낸다. 그래서 실패 스택에서 테스트 파일을 가리키는
  **가장 바깥 프레임**이 그 케이스의 선언 뒤 · 다음 케이스 선언 앞이고, 그 사이에 훅 선언이 없을 때만 «본문» 으로 본다
  (본문 실패의 가장 바깥 테스트 파일 프레임은 러너가 부른 테스트 콜백 자신이고, 준비 단계 실패면 훅 콜백이다).
- 본문에 단언이 여럿이면 그중 어느 것이 «회귀를 재려던 단언» 인지는 보고서로 증명할 수 없다. 검출은 «본문 단언이 뒤집혔다» 까지만 주장한다.
  기록과 PR 에 실패한 단언의 메시지와 위치를 그대로 싣는다. 못 박으려면 `--expect` 로 기대 실패 문자열을 준다.
- 단언 오류 판별: Vitest 는 플러그인이 함께 넘기는 보고기가 오류 객체에서 읽는다(chai `AssertionError` · `expect.extend` 단언 ·
  스냅샷 불일치 — 이름은 `Error` 지만 Vitest 자신도 `Snapshot … mismatched` 메시지로 가린다).
  Jest 는 JSON 보고서의 `failureDetails[].matcherResult` 로 읽는다. Testing Library 의 `getBy*` 실패처럼 단언이 아닌 오류는 원인 미확인이다 —
  단언(`expect(...)`)으로 바꾸면 검출로 센다.
- 대상이 아닌데 뒤집힌 케이스는 «참고» 로만 남고 집계에 들어가지 않는다.

## 4. 격리본 — 사용자 작업 트리는 건드리지 않는다

1. 현재 작업 내용(git 추적 + 무시되지 않은 미추적 파일)을 임시 폴더에 복사한다. 선언한 추가 입력(`copy`)도 함께.
2. `node_modules` 는 복사하지 않고 이어 붙인다 — 링크 항목은 링크 그대로(상대 링크는 격리본 안에서 다시 풀린다), `@scope` 묶음 폴더는 격리본에
   만들고 안을 항목별로, 그 밖의 폴더 · 파일은 원본으로 링크, 캐시 폴더(`.vite` · `.vitest-cache` · `.cache` 등)는 가져오지 않는다(링크하면 격리본의 러너가 원본 캐시에 쓴다).
3. **자기 점검 ①** 테스트 패키지 위치에서 워크스페이스 패키지 이름을 Node 해석 순서로 찾아 실제 경로가 격리본 안인지 본다.
   원본 소스로 풀리면 측정 불가(«격리 불가»). 이 점검이 없으면 수정 전 상태를 재는 줄 알고 현재 코드를 재게 되고 조용히 미검출이 나온다.
4. **자기 점검 ②** 대조로 내용이 바뀌는 워크스페이스 패키지가 빌드 결과물(작업 트리 파일 목록에 없는 `dist` 등)을 내보내면, 대조 소스를 바꿔도
   테스트가 기존 결과물을 읽어 통과할 수 있다. 준비 명령(`prepare`)을 선언하지 않았으면 측정 불가로 끝낸다. 선언했으면 양쪽 격리본에서 각각 돌린다.
5. 격리본에는 저장소의 심볼릭 링크가 링크 그대로 들어간다. 그래서 둘째 격리본에 대조 내용을 쓰거나(수정 전 대조 · 지정 변이) 선언한 추가 입력을 복사할 때,
   격리본 루트부터 그 경로까지 이미 있는 마디가 하나라도 링크면 쓰지 않고 측정 불가(«격리 불가»)로 끝낸다 — 링크를 따라 원본 파일에 쓰지 않기 위해서다.
   기준 리비전에서 심볼릭 링크였던 소스도 대조하지 않는다.
6. 이 격리본을 **그대로 복제**해 둘을 만든다(같은 입력). 첫째는 현재 소스, 둘째는 제품 소스만 대조 내용으로 바꾼다. 한 격리본을 다시 쓰지 않는다 —
   첫 실행이 남긴 파일(상태 파일 · 스냅샷 · 캐시)이 둘째 결과를 바꿀 수 있다.
7. **보정 실행**: 첫째 격리본에서 대상 케이스가 통과하고 파일 · 러너 수준 오류가 없을 때만 대조 실행으로 간다. 아니면 측정 불가
   (격리본에는 git 이 무시하는 파일이 없어 환경 차이로 실패할 수 있다 — 필요한 파일은 `copy` 로 선언한다).
8. 러너는 테스트 패키지에서 프로젝트 루트까지 올라가며 러너 설정(`vitest.config.*` · `vite.config.*` · `jest.config.*` · `package.json` 의 `jest`)이 처음 보이는 폴더에서 돈다
   (설정이 루트에만 있는 워크스페이스 — Vitest 는 설정을 위로 찾지 않는다). 러너 옵션(자동 감지일 때): 스냅샷 **읽기 전용**(Vitest `--update=none` · Jest `--ci`), 커버리지 끔, 재시도 끔. 기준 스냅샷이 없는 스냅샷 테스트는
   보정 실행에서 실패해 측정 불가가 된다(두 격리본이 각자 스냅샷을 새로 쓰고 둘 다 통과하는 일을 막는다).
9. 실행마다 시간 상한(기본 120초). 넘으면 프로세스 그룹째 끝내고 측정 불가. 끝나면 격리본을 지운다(강제 종료로 남은 것은 6시간 뒤 다음 실행이 지운다).
10. 격리본의 `node_modules` 는 원본을 링크로 본다. 그래서 격리본 안에서 의존성을 **설치 · 변경하는 명령은 원본에 쓸 수 있다** — 준비 명령에 넣지 않는다.
   실행기는 격리본 안의 모든 명령에서 pnpm 의 실행 전 의존성 확인(`verify-deps-before-run`)을 끈다(원본 경로를 담은 상태 파일 때문에 격리본에서
   늘 «낡음» 으로 판정해 스스로 install 을 시도한다 — pnpm 11 실측). 실제 러너 eval 은 모든 시나리오 뒤 원본 `node_modules` 가 그대로인지 확인한다.

## 5. 파일 분류와 적용 관계

| 분류 | 기본 기준 | 격리본에서 |
|---|---|---|
| 실행할 테스트 | 러너의 기본 수집 규칙 — `*.test.*` · `*.spec.*`, Jest 면 `__tests__/` 아래 코드 파일도. E2E 경로(`e2e/` · `playwright/` · `cypress/` · `*.e2e.*`)는 제외 | 현재 내용 유지 · 러너에 넘긴다 |
| 지원 파일 | `__mocks__/` · `__fixtures__/` · `fixtures/` · `__snapshots__/` · `*.snap` · `test(s)/` · 테스트 준비 파일 · E2E 경로 | 현재 내용 유지 · 두 격리본에 똑같이 |
| 설정 | `package.json` · 잠금 파일 · `tsconfig*.json` · `*.config.*` 등 | 현재 내용 유지 · 바뀌었으면 «대조에 넣지 않음» 으로 기록 |
| 제품 소스 | 코드 · 스타일 · 데이터 파일 중 위가 아닌 것 | 대조 내용으로 바꾼다(수정이 만든 파일은 지우고, 지운 파일은 되살린다) |
| 무관 | 문서 등 그 밖 | 현재 내용 유지 |

- 러너 설정으로 수집 규칙을 바꿨다면(예: Vitest `include` 에 이름 관례 밖의 패턴) 선언 `testPaths` 로 알려 준다 — 훅은 러너를 실행하지 않고 이 규칙으로 판단한다.
  실행기는 러너가 실제로 수집하지 않은 파일을 «케이스 미수집 · 측정 불가» 로 드러낸다.
- **적용 관계**: 대조하는 제품 소스는 «그 테스트를 돌리는 패키지(가장 가까운 `package.json`)» 와 그 패키지가 의존하는 워크스페이스 패키지(전이적)
  안의 것만이다. 한 앱의 소스와 다른 앱의 테스트가 같은 턴에 바뀌었다고 대조하지 않는다.

## 6. 기록과 재사용

기록은 `git rev-parse --git-path fe-rail/verify/records` 아래에 실행마다 JSON 하나(추적되지 않음 · 워크트리마다 따로 · 최근 300개).
기록이 요청을 충족하려면 — 종료 훅 · fe-start · `status` 가 같은 판정을 쓴다:

1. 입력이 같다 — 검증 트리 id(fe-start 와 같은 계산 · 미추적 포함) + 선언한 추가 입력(`copy`)의 내용 지문(git 이 무시하는 파일은 트리 id 에 안 잡힌다).
2. 기준 리비전 · 테스트 명령 · 준비 명령이 같다(지정 변이 기록은 기준 대신 같은 트리의 변이로 인정).
3. 범위가 전체다 — 부분 대조 기록은 전체 확인 요청을 충족하지 않는다.
4. 그 파일에서 확인해야 할 케이스(새 케이스 추정) 전부를 유효한 기록들의 대상이 덮는다 — A 만 확인한 기록으로 B 를 확인한 것으로 치지 않는다.

`--expect` 가 다르면 저장한 실패 근거(오류 종류 · 메시지 · 본문 여부)로 다시 판정한다 — 재실행 없이 검출 ↔ 원인 미확인이 갈린다.
테스트 · 제품 소스 · 지원 파일 · 설정 · 선언한 추가 입력 중 무엇이든 바뀌면 기록은 무효다.

## 7. 소비 프로젝트 조정

**선언** — 테스트 패키지 → 프로젝트 루트 → git 루트 순으로 처음 찾은 `package.json` 의 `"fe-rail": { "testVerify": { … } }`:

| 키 | 뜻 |
|---|---|
| `command` + `format` | 테스트 명령 틀. 자리표시자 `{files}`(패키지 기준 상대 경로) · `{out}`(JSON 보고서 경로) · `{reporter}`(Vitest 보고기 경로). `format` = `vitest` · `jest` · `exit-code`(기본). 앱 선택 환경변수 등이 필요할 때 쓴다. Vitest 는 `{reporter}` 를 `--reporter={reporter}` 로 넘겨야 단언 · 위치를 정밀 판정한다(없으면 `AssertionError` 문자열만으로 판정 — `expect.extend` 단언은 원인 미확인). 선언 명령은 «검증된 조합» 이 아니라 훅이 막지 않는다 |
| `prepare` | 격리본 준비 명령(프로젝트 루트에서 · 양쪽 격리본에서 각각). 빌드 결과물을 소비하는 구성용 |
| `copy` | 격리본에 더 넣을 git 무시 파일 · 폴더(선언한 `package.json` 기준 상대 경로). 내용 지문이 기록 유효성에 들어간다 |
| `testPaths` · `supportPaths` · `e2ePaths` | 분류 보강(저장소 루트 기준 접두 경로 또는 `*` · `**` 글롭) |

```json
{ "fe-rail": { "testVerify": { "prepare": "npm run build -w @acme/ui", "copy": [".env.test"] } } }
```

> **신뢰 수준** — `command` · `prepare` 는 저장소가 정한 셸 명령이고 실행기가 격리본 안에서 그대로 실행한다. 저장소의 테스트 설정(`vitest.config.*` 등)과 테스트 파일을 실행하는 것, 곧 `npm run test` 와 같은 수준이다. 신뢰하지 않는 저장소에서는 실행기도 테스트도 돌리지 않는다.
> 종료 훅은 선언 `command` 를 쓰는 구성(검증된 조합이 아님)에서는 실행을 지시하지 않고 알림만 낸다.

**환경변수**: `FE_RAIL_VERIFY_TIMEOUT`(초 · 120) · `FE_RAIL_VERIFY_MAX_SOURCES`(50) · `FE_RAIL_VERIFY_MAX_TESTS`(훅이 막는 상한 · 10) ·
`FE_RAIL_VERIFY_MAX_FILES`(격리본 파일 수 · 100000) · `FE_RAIL_VERIFY_MAX_MB`(4096) · `FE_RAIL_VERIFY_MAX_DIRTY`(턴 기록 · 2000).
끄기: `FE_RAIL_DISABLED_HOOKS="test-verify"` 또는 `FE_RAIL_HOOK_PROFILE=minimal`.

## 8. 지원 상태

종료 훅의 **자동 차단은 검증된 조합에서만** 켠다 — 고정 버전 fixture 로 실제 러너를 돌리는 eval(`eval/runner.mjs`)을 통과한 패키지 매니저 × 러너
메이저. 그 밖의 조합에서도 실행기는 직접 부를 수 있다(훅은 알림만). 워크스페이스 패키지를 소스 그대로 소비하는 구성이 기본이고,
빌드 결과물을 소비하면 `prepare` 를 선언해야 대조한다.

| 조합 | 상태 |
|---|---|
| npm · pnpm + Vitest 4 (eval 고정 4.1.9) | 자동 지원 |
| npm · pnpm + Vitest 5 (eval 고정 5.1.0) | 자동 지원 |
| npm + Jest 30 (eval 고정 30.2.0) | 자동 지원 |
| Yarn 클래식 · bun · 그 밖의 버전 | 미검증 — 실행기는 동작할 수 있으나 훅은 막지 않는다 |
| Yarn PnP | 첫 릴리스에서 자동 지원하지 않음(측정 불가) |
| 그 밖의 러너 | 선언 `command` + `format: exit-code` — 종료 코드로 «결과 차이» 까지만 본다 |
| E2E 러너 · git 이 아닌 폴더 | 대상 아님 |

UI 프레임워크에는 의존하지 않는다. 실행 환경은 Claude Code 세션(훅)이고, 서브에이전트 세션에는 턴 시작 훅이 없어 종료 훅이 작동하지 않는다.

## 9. 미검출 · 원인 미확인 · 측정 불가를 읽는 법

0. **측정이 유효했는가.** 대상 케이스가 실제로 실행됐는가(출력의 대상 목록 · `추정` 표시), 현재 소스에서 통과했는가, 대조 소스에서 의도한 단언에서
   실패했는가(실패 메시지 · 위치).
1. **원인 미확인을 읽는 법.** 사유를 본다 — 준비 · 정리 단계에서 실패했는지, 본문의 일반 예외(`TypeError` 등)인지, 시간 초과인지.
   본문 예외가 결함의 진짜 증상이면 그 증상을 단언으로 잡도록 테스트를 고친다(예: 값이 `undefined` 라 죽는다면 그 값을 먼저 단언한다).
2. **변이가 테스트의 목(mock) 안쪽 층에 있다.** 테스트가 모듈 A 를 목으로 대체하고 A 의 인자만 단언하면, A 안쪽을 바꾼 대조는 원리적으로 못 잡는다.
   그 층을 소유한 테스트(A 자체의 테스트)에 따로 쓴다. 이것을 «등가 변이» 로 적으면 거짓 기록이다 — 동작은 바뀌었고 관측 밖이었을 뿐이다.
3. **단언이 제목과 반대다.** «X 하면 Y 가 보인다» 라는 테스트가 Y 의 부재를 단언하면 결함이 있어도 통과한다. 제목과 단언을 대조한다.
4. **변이가 그 계약을 건드리지 않았다.** 테스트도 단언도 멀쩡한데 바꾼 곳이 그 테스트가 재는 동작이 아니면 통과가 맞다. 테스트가 아니라 변이를 바꾼다
   (여기서 테스트를 고치면 멀쩡한 테스트를 망가뜨린다).
5. **변이가 의도한 자리에 들어가지 않았다.** `--find` 유일성 검사가 대부분 막지만, 유일한 «다른» 자리를 고른 경우는 남는다. 출력의 대조 소스와 변이 내용을 본다.
6. **픽스처 값이 하필 정답과 같거나, 픽스처가 그 상태를 만들 수 없다.** 잘못된 값이 나가도 대표 데이터가 그 값과 같으면 단언이 통과한다.
   반대로 픽스처가 그 필드를 고정값으로 박아 두면 그 상태를 표현할 수 없다. 세 번째 값을 가진 픽스처를 쓴다.

측정 불가는 사유대로 고친다: 기준 스냅샷 없음 → 현재 상태의 스냅샷을 먼저 커밋 · 갱신 / 파일 로딩 실패(새 기능) → `mutate` /
빌드 결과물 → `prepare` / 대조할 소스 차이 없음 → `--base` / 격리 환경 불일치 → `copy` 로 필요한 무시 파일 선언 / 이름 중복 → `--test` 를 고유한 이름으로.

공용 로직의 여러 분기 · 경계값을 한꺼번에 재려면 범위를 지정한 자동 변이 도구(예: StrykerJS 의 `파일:시작줄-끝줄` 범위)가 더 맞다.
